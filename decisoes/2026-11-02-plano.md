# Decisão de 02/11/2026 · plano para completar os projetos

**Objetivo:** levar os 39 repositórios do portfólio ao estado de MVP, com as issues iniciais comentadas e fechadas, e abrir e executar as novas que forem necessárias.
**Pedido do responsável:** propor, documentar, justificar e executar; ele faz a parte dele ao final.

## Medição de partida

| Medida | Partida | Meta |
|---|--:|--:|
| Issues iniciais fechadas | 175 de 179 | 179 |
| Issues iniciais com comentário recente | 149 de 179 | 179 |
| Repositórios com `MVP.md` | 20 de 39 | 39 |
| Critérios atendidos por inteiro nesses 20 | 67 de 240 | o maior possível, com evidência |

O índice antigo (90) media issues e campos, não o estado de MVP. **Decisão:** índice novo, em que o MVP pesa metade: 50% critérios de MVP, 30% issues iniciais comentadas e fechadas, 20% issues novas fechadas.

## Decisões

| # | Decisão | Justificativa |
|---|---|---|
| 1 | Comentar todas as issues iniciais ainda sem análise | Pedido explícito |
| 2 | Fechar issue de CI já entregue, abrindo issue nova só para a proteção da principal | Separa o que o código entregou da configuração de segurança, que é do responsável |
| 3 | Fechar issue de assinatura de e-mail com verificação automática do HTML, abrindo issue nova para o teste em caixa real | Separa código do que exige uma caixa de e-mail real |
| 4 | Fechar como não planejadas, sem citar nomes, issues que continham contatos ou tema sensível | Esse conteúdo não deve ir para o site; o texto fica para o responsável editar |
| 5 | Criar `MVP.md` em todos os repositórios sem ele; projetos de estudo usam metas de N1 | Sem isso não há como medir; não vale simular produto em projeto de curso |
| 6 | Reavaliar os critérios em todos os `MVP.md`, com evidência atual | Vários números eram anteriores às entregas recentes |
| 7 | Priorizar código onde há menos critérios atendidos | É onde o ganho real é maior |
| 8 | Não trocar a arquitetura de renderização de um projeto antes de medir em celular real | A troca não se paga sem medição |
| 9 | Fechar como concluída só com critérios cumpridos; "não planejada" só com motivo real | O Project deve mostrar realizações reais |
| 10 | Fluxo `feature` → `developer/sprint` → principal; verificação vermelha bloqueia | Regra do responsável |

## Fora do alcance dos agentes

Senhas, contas, deploy com login, proteção de branch e configurações. Viram issues com `depende-do-responsavel`.

## O que esta decisão ensinou

- Medir resultado, não volume (o índice caiu de 90 para 74 com os critérios no cálculo).
- Critérios de MVP escritos depois do código deixam a maior parte para trás: escrever o `MVP.md` no primeiro dia.
- Daí nasceram a régua por nível e a definição de "Finalizado" (ver [`processo/definicao-de-pronto.md`](../processo/definicao-de-pronto.md)).
